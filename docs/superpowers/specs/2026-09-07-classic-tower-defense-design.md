# 클래식 타워 디펜스 웹게임 — 설계 문서

- 날짜: 2026-09-07
- 상태: 승인됨 (구현 계획 단계로 진행)

## 1. 개요

브라우저에서 동작하는 클래식 타워 디펜스 웹게임. 정해진 경로를 따라 오는
적을 타워로 막아내는 표준적인 TD 장르로, 로그라이크/카드 배치나 미로형
경로 조작 같은 변형 요소는 넣지 않는다.

**테마**: 현대 좀비 아포칼립스 — 플레이어는 거점을 지키는 군대/민병대
지휘관 역할이며, 타워는 병과(소총수/기관총/저격수 등), 적은 좀비 변종으로
표현한다.

**MVP 스코프**
- 맵 3개 (각기 다른 경로 형태와 웨이브 구성)
- 타워 7종 (전투형 5종 + 지원형 2종)
- 적 6~8종 + 맵당 보스 1종
- 비주얼: 이미지/스프라이트 없이 도형(원, 사각형 등) + 색상만으로 표현
- 저장: 브라우저 `localStorage`만 사용 (계정/로그인 없음)
- 장기적으로 백엔드 연동을 고려하되, 지금은 순수 프론트엔드로 구현

## 2. 기술 스택

- Vite + Vue 3 (Composition API, `<script setup>`) + TypeScript
- 렌더링: `<canvas>` 2D context (Vue는 UI 셸만 담당)
- 테스트: Vitest (엔진 유닛 테스트), Vue Testing Library (가벼운 UI 테스트)

## 3. 아키텍처

### 3.1 계층 구조

- **게임 엔진 (`GameEngine`)**: Vue/DOM에 의존하지 않는 순수 TypeScript
  클래스. 맵, 타워, 적, 투사체, 웨이브, 골드/라이프 상태를 전부 소유하고
  `update(dt)` 호출로 한 프레임만큼 시뮬레이션을 진행한다.
- **렌더러 (`Renderer`)**: 매 프레임 `GameEngine`의 현재 상태를 읽어
  캔버스에 도형으로 그리기만 하는 상태 없는(stateless) 함수/클래스.
- **Vue 레이어**: `GameCanvas`(rAF 루프 실행, engine.update + renderer.draw
  호출), `HUD`(골드/라이프/웨이브/시작 버튼), `TowerShop`(타워 선택),
  `MapSelect`, `GameOverModal` / `VictoryModal`.

### 3.2 엔진 ↔ Vue 연결

- 적/투사체처럼 매 프레임 바뀌는 값은 Vue의 반응형 상태(`ref`/`reactive`)에
  절대 넣지 않고 캔버스에 직접 렌더링한다 (Vue 리렌더 비용을 피해 성능을
  확보하기 위함).
- 골드, 라이프, 현재 웨이브 번호, 게임 상태(진행중/승리/패배)처럼 드물게
  바뀌는 값만 엔진이 이벤트(pub/sub)로 발행하고, Vue는 이를 구독해
  해당 값이 바뀔 때만 리렌더한다.
- Vue → 엔진으로의 명령은 `engine.placeTower(pos, type)`,
  `engine.startNextWave()` 같은 명령형 메서드 호출로 이루어진다.

### 3.3 지원형 타워(버프) 처리

- 전투형 타워는 각각 `damage`/`range`/`fireRate` 같은 정적 스탯을 갖지만,
  지원형 타워(4.2절 "사령관", "DJ")는 주변 전투형 타워의 유효 스탯을 매 틱
  끌어올린다. 이를 위해 `Tower` 인스턴스에 `buffMultiplier`(기본값 1)
  필드를 두고, `GameEngine.update(dt)`가 매 틱 시작 시 모든 타워를 순회하며
  "이 타워가 몇 개의 지원형 타워 사거리 안에 들어와 있는가"를 계산해
  `buffMultiplier`를 갱신한다. `Tower.range`/`Tower.damage`
  게터와 `resetCooldown()`이 이 배수를 반영하므로, 버프 로직은 전적으로
  `GameEngine`에 있고 `Tower`는 배수 하나만 알면 된다.
- 지원형 타워도 동일한 `range`/`buffMultiplier` 메커니즘을 그대로 써서
  "버프 반경"을 표현한다 — 즉 지원형 타워가 다른 지원형 타워의 범위 안에
  들어가면 그 자신의 버프 반경과 버프 강도도 함께 커지는 자연스러운 중첩
  효과가 생긴다(의도된 동작).
- 지원형 타워는 `findTarget`/발사 로직에서 제외되어 스스로는 절대 공격하지
  않는다.
- **사령관**은 위 메커니즘을 그대로 사용해 반경 내 전투형 타워의
  데미지/공속/사거리를 동시에 올린다(고정 버프, 모드 없음).
- **DJ**는 세 가지 모드(`range`/`damage`/`discount`) 중 하나만 활성화되고,
  플레이어가 DJ 타워를 클릭할 때마다 다음 모드로 순환 전환된다
  (`engine.cycleSupportMode(towerId)`). `range`/`damage` 모드는 사령관과
  동일한 `buffMultiplier` 경로를 타되 해당 스탯만 올린다. `discount` 모드는
  전투 스탯에 전혀 영향을 주지 않는 대신, DJ 사거리 안에 있는 타워의
  **업그레이드 비용**을 낮춘다 — `GameEngine`이 업그레이드 비용을 계산할
  때(`getUpgradeCost(tower)`) 해당 타워가 discount 모드 DJ의 범위 안에
  있는지 확인해 할인율을 적용한다. 즉 discount는 `buffMultiplier`가 아닌
  별도의 경제 계산 경로로 처리된다.

### 3.5 특수 공격 메커닉 (버스트/예열/화상)

기본 전투형 타워는 "쿨다운 후 즉시 발사 1회"로 충분하지만, 아래 세 타워는
발사 로직에 상태를 추가로 요구한다.

- **솔져 (버스트)**: 발사 시 단일 투사체가 아니라 짧은 간격으로 3발을
  순차 발사한다(발당 3데미지, 총 9). 버스트 도중에는 `fireRate` 쿨다운이
  적용되지 않고, 3발이 모두 나간 뒤에야 다음 쿨다운이 시작된다. `Tower`에
  `burstShotsRemaining`/`burstTimer` 상태를 둔다.
- **미니거너 (예열)**: 사거리 안에 유효 타겟이 처음 들어오면 곧바로
  발사하지 않고 2초간 `spinUpTimer`를 채운 뒤 발사를 시작한다. 예열 도중
  타겟을 완전히 잃으면(사거리 밖으로 나가고 대체 타겟도 없으면)
  `spinUpTimer`가 0으로 리셋된다. 예열이 끝난 뒤로는 `fireRate`(매우
  빠름)로 계속 발사한다.
- **화염방사병 (화상 DoT)**: 명중한 적에게 `burning` 상태(5초 지속, 1초마다
  3데미지 틱)를 부여한다. `Enemy`가 `burnTicksRemaining`/`burnTickTimer`를
  들고 있고 `GameEngine.update(dt)`가 매 틱 소각 데미지를 적용한다. 화상
  중인 적이 다시 맞으면 지속시간을 5초로 갱신한다(스택 없이 갱신만, 이중
  적용으로 인한 데미지 폭증 방지).

### 3.6 저장 계층

- `SaveService` 인터페이스를 정의하고, 지금은 `LocalStorageSaveService`만
  구현한다. 나중에 백엔드가 추가되면 `RemoteSaveService` 구현체로 교체하는
  것만으로 전환 가능하도록 게임 엔진/저장 로직을 UI와 분리해 둔다.

## 4. 주요 데이터 모델

### 4.1 맵 (Map)

- 그리드 크기, 적 이동 경로(`path`: 웨이포인트 좌표 배열), 타워 설치 가능
  타일 목록을 JSON으로 정의.
- 맵 3개는 각각 다른 경로 형태와 웨이브 구성으로 난이도를 차별화하며,
  좀비 아포칼립스 테마에 맞춰 배경 설정을 부여한다:
  1. 폐허가 된 시가지 거리 (구불구불한 경로)
  2. 고속도로 검문소 (직선+분기 경로)
  3. 군 기지 정문 (좁고 방어선이 겹치는 경로)

### 4.2 타워 (Tower)

- 공통 필드: `cost`, `range`, `damage`, `fireRate`, `projectileSpeed`,
  `targetingStrategy`(가장 가까운 적 / 가장 체력 많은 적 / 가장 먼저
  들어온 적).
- 업그레이드 개념 포함: 레벨업 시 데미지/사거리 증가, 골드 소모.

**전투형 5종**

| 타워 | 무기 컨셉 | 데미지 | 사거리 | 공속 | 비용 | 비고 |
|---|---|---|---|---|---|---|
| 스카웃 | 권총 | 발당 2 | 무난 | 준수 | 낮음 | 기본 타워 |
| 솔져 | 3점사 소총 | 발당 3, 버스트당 9 | 무난 | 빠름 | 중간 | 3.5절 버스트 |
| 스나이퍼 | 저격소총 | 발당 15 | 매우 긺 | 느림 | 높음 | 단일 대상 고데미지 |
| 미니거너 | 미니건 | 발당 6 | 긺 | 매우 빠름 | 높음 | 3.5절 예열(2초) |
| 화염방사병 | 화염방사기 | 스플래시 + 화상 DoT | 짧음 | - | - | 3.5절 화상(5초, 틱당 3) |

**지원형 2종**

- **사령관**: 직접 공격하지 않고, 사거리(=버프 반경) 안의 모든 전투형
  타워에게 데미지/공속/사거리를 함께 올려준다(고정 버프, 3.3절). 비용은
  중간. 여러 대를 겹쳐 설치하면 버프가 중첩 누적된다.
- **DJ**: 직접 공격하지 않고, 클릭할 때마다 `사거리` / `데미지` / `할인`
  세 모드를 순환 전환한다(3.3절). `사거리`/`데미지` 모드는 사령관과 같은
  방식으로 해당 스탯만 올리고, `할인` 모드는 전투 스탯 대신 반경 내
  타워의 업그레이드 비용을 낮춘다. 비용은 높음.
- 두 지원형 모두 캔버스에서 전투형과 다른 색으로 그려지고, 버프 반경을
  항상 반투명 원으로 표시한다(전투형 타워는 선택/배치 시에만 사거리를
  보여준다). DJ는 현재 모드를 아이콘/색상 틴트로 구분해 표시한다.

### 4.3 적 (Enemy)

- 필드: `hp`, `speed`, `reward`(처치 시 골드), 경로 진행률.
- 좀비 변종으로 표현: 일반 좀비(밸런스형), 러너 좀비(빠르지만 약함),
  탱커 좀비(느리지만 체력 높음), 크롤러(작고 빠른 다수 스폰형). 나머지
  1~2종은 밸런싱 단계에서 확정한다.
- 화상(3.5절) 등 상태 이상을 받을 수 있도록 `burnTicksRemaining`/
  `burnTickTimer` 필드를 갖는다(화상 중이 아니면 0).
- 보스는 맵마다 다른 "변이체" 컨셉(예: 거대 변이 좀비, 방탄 갑옷 좀비)의
  별도 타입으로, 훨씬 높은 hp와 고유 보상을 가진다.

### 4.4 투사체 (Projectile)

- 발사한 타워, 타겟 적, 데미지, 이동 속도를 가진 단순 객체.
- 스플래시(범위) 데미지 여부는 발사한 타워 종류에 따라 결정된다.

### 4.5 웨이브 매니저 (WaveManager)

- 맵마다 웨이브 목록(각 웨이브의 적 구성과 스폰 타이밍)을 정의.
- 마지막 일반 웨이브 클리어 시 보스 웨이브를 트리거한다.

### 4.6 경제 (Economy)

- 시작 골드, 적 처치 보상, 타워 설치/업그레이드 비용을 엔진이 관리.
- 적이 경로 끝에 도달하면 라이프가 감소하고, 라이프가 0이 되면 게임오버.
- DJ의 `discount` 모드(3.3절)는 이 비용 계산 경로에 개입해 반경 내 타워의
  업그레이드 비용만 낮춘다.

### 4.7 비주얼 표현 (도형/색상 매핑)

이미지/스프라이트 없이 도형+색상만 사용하는 MVP 제약(1절)을 좀비
아포칼립스 테마에 맞춰 다음과 같이 매핑한다.

- 좀비(적): 초록/올리브 계열 색상의 원.
- 전투형 타워: 카키/회색 계열 색상의 사각형.
- 지원형 타워(사령관, DJ): 전투형과 구분되는 별도 색상(예: 주황 계열)의
  사각형. DJ는 현재 활성 모드에 따라 틴트를 다르게 표시한다(4.2절).
- 보스: 일반 좀비보다 크고 진한 색상의 원으로 강조.

## 5. 데이터 흐름

1. `requestAnimationFrame` 루프가 프레임 간 시간(`dt`)을 계산하고
   `engine.update(dt)`를 호출한다.
2. 엔진 내부에서: 적을 경로 따라 이동 → 타워가 사거리 내 적을 탐색해
   투사체 발사 → 투사체 이동 및 충돌 판정 → 죽은 적 제거(골드 지급) →
   웨이브 종료/라이프 감소 체크 순으로 처리한다.
3. `renderer.draw(ctx, engine.getState())`로 캔버스에 현재 프레임을 그린다.
4. 골드/라이프/웨이브/게임 상태가 바뀐 경우에만 엔진이 이벤트를 발행하고,
   Vue HUD는 그때만 리렌더한다.
5. 사용자 입력(캔버스 클릭으로 타워 배치, HUD 버튼으로 웨이브 시작)은
   Vue에서 `engine.xxx()` 메서드 호출로 엔진에 전달된다.

## 6. 에러 처리

- 타워 배치 실패(자리 없음/골드 부족)는 예외를 던지지 않고
  `{ success: false, reason }` 형태로 반환하며, UI는 짧은 토스트/인라인
  메시지로 안내한다.
- 라이프가 0이 되면 엔진은 루프를 멈추고 `game-over` 이벤트를 발행하며,
  Vue는 이를 받아 모달을 표시한다 (크래시 없이 정상 종료 흐름으로 처리).
- `localStorage`에 저장된 데이터가 손상되었거나 버전이 맞지 않는 경우
  `LocalStorageSaveService`가 파싱 실패를 잡아 `null`을 반환하고,
  이는 "저장된 게임 없음"으로 취급되어 앱이 죽지 않는다.

## 7. 테스트 전략

- 게임 엔진(타워 타겟팅, 데미지 계산, 웨이브 스폰, 경제 로직)은
  DOM/Vue에 의존하지 않으므로 Vitest로 순수 유닛 테스트를 작성한다.
  이 프로젝트에서 가장 중요한 테스트 영역이다.
- HUD/상점 등 Vue UI는 버튼 클릭이 엔진 메서드를 올바르게 호출하는지
  정도만 Vue Testing Library로 가볍게 검증한다.
- 캔버스 렌더링 자체와 밸런스(골드 곡선, 난이도 곡선)는 자동 테스트보다
  수동 플레이테스트로 확인한다.

## 8. 스코프 밖 (Out of Scope, 이번 MVP 기준)

- 멀티플레이어, 계정/로그인, 백엔드 연동 (장기 고려 사항으로만 남김)
- 이미지/스프라이트 에셋 (도형 기반 비주얼만 사용)
- 로그라이크 카드 배치, 미로형 경로 조작 등 클래식 TD를 벗어나는 변형 요소

## 9. 향후 로드맵 (MVP 이후, 이번 구현 범위 아님)

- **난이도 선택(쉬움/보통/어려움)**: 맵 선택 화면에서 난이도를 고르면
  시작 골드/라이프, 적 스탯 배율(hp/speed) 등에 배율을 적용하는 구조.
  MVP 완성 후 별도 브레인스토밍 세션에서 설계한다.
